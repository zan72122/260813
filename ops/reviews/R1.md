### R1-01 — Gait.walkTo() が前回のPromiseを解決せずに上書きする(jumpTo("seek")スタールの根本原因)
- **severity**: major
- **confidence**: high
- **evidence**: `src/scene/elephant/gait.ts:106-112`
  ```ts
  walkTo(points: Vec3Like[]): Promise<void> {
    const pts = points.map((p) => new THREE.Vector3(p.x, 0, p.z));
    if (pts.length === 0) return Promise.resolve();
    return new Promise((resolve) => {
      this.task = { points: pts, index: 0, resolve };   // ← 既存taskがあっても無条件に上書き
    });
  }
  ```
  `this.task`に前回のタスクが残っていても`resolve`を呼ばずに新タスクで上書きするため、前回の
  `walkTo()`が返したPromiseは**永久に未解決のまま**になる(reject もされない)。
  `Elephant.enter()`(`src/scene/elephant/elephant.ts:135-138`, `await this.gait.walkTo([...])`)と
  `Elephant.walkToSpot()`(同`:153`, `await this.gait.walkTo([spot.approach])`)がともにこの
  `walkTo()`を使う。
  `src/ui/app.ts:233-236`の`prepareForPhase("seek")`:
  ```ts
  case "seek": {
    void world.openGate().then(() => world.elephantEnter());  // await していない
    events.emit("gate:opened", {});
    break;
  }
  ```
  この直後に`fsm.transition("seek")`→`mountSeekScreen`→`run()`が`ctx.world.elephantSeek()`
  (`elephant.walkToSpot`経由)を即座に呼ぶため、`elephantEnter()`内の`walkTo`タスクが完了する前に
  `walkToSpot()`の`walkTo`が`this.task`を上書きし、`enter()`のPromiseが永久にstallする。
  `elephant.state`も`"entering"`のまま次のステップ(`"sniffing"`→`"idle"`)へ進めなくなる。
- **affected files**: `src/scene/elephant/gait.ts`, `src/scene/elephant/elephant.ts`,
  `src/ui/app.ts`
- **reproduction**: `?qa=1&act=seek`(または`debugApi.jumpTo("seek")`)で起動 →
  `window.__elephantDebug`の`state`が`"entering"`のまま変化しない/`elephantEnter()`のawait元が
  進行しないことを確認できる(`ops/reports/S6.md`が報告した既知バグの再現と一致)。
  **通常のゲームプレイ経路(`src/ui/screens/gate.ts:96-110`の`triggerOpen()`)では
  `await ctx.world.elephantEnter()`を`ctx.transition("seek")`より前に完了させているため発生しない**
  ことをコードで確認した(この点はS6の記録と一致)。QA専用の実害。
- **suggested fix**: `Gait.walkTo()`内で既存`this.task`がある場合は新タスク設定前に
  `const prev = this.task; this.task = null; prev?.resolve();`で前タスクを明示的に解決してから
  上書きする(`stop()`と同じ処理を先頭で呼べばよい)。加えて`prepareForPhase("seek")`を
  `async`化し`await`することが望ましい(ただし`app.ts`は現状の設計方針として`case "seek"`のみ
  意図的に発火のみにしている旨`ops/reports/S4.md`に明記あり、変更時は要検討)。

### R1-05 — 本番ビルドで `hideFoodDirect` が qa 判定なしに実際に機能する(debug機能の本番漏出、新規発見)
- **severity**: major
- **confidence**: high
- **evidence**: `src/main.ts:148-156`
  ```ts
  const debugApiHandle = window.__ELEPHANT_GAME_DEBUG__ as unknown as Record<string, unknown> | undefined;
  if (debugApiHandle) {
    debugApiHandle.hideFoodDirect = (spotId, food) => app.hideFoodDirect(spotId, food);
  }
  ```
  この代入は`config.qa`を一切チェックしていない。`window.__ELEPHANT_GAME_DEBUG__`自体は
  `installDebugApi(config.qa)`により**qa未指定でも常に生成される**(`src/debug/qa.ts:119-123`)ため、
  本番ビルド(`?qa=1`なし)でも`window.__ELEPHANT_GAME_DEBUG__.hideFoodDirect(spotId, food)`を
  コンソールから呼び出すと、`DebugController`の他メソッド(`jumpTo`/`setQuality`等、
  `src/debug/qa.ts`側で`if (!this.qaMode) { warn; return; }`により本番ではno-op化される)とは違い、
  **no-op化されず実際にセッションへ食材を直接配置してしまう**。
  `docs/INTERFACES.md:169`「本番でも ready/getState のみ露出」という契約に対する明確な逸脱。
- **affected files**: `src/main.ts`
- **reproduction**: `npm run build && npm run preview`後、`?qa=1`なしでアプリを開き、hide画面へ進んだ
  状態でブラウザconsoleから`window.__ELEPHANT_GAME_DEBUG__.hideFoodDirect("sand","hay-cube")`を
  実行すると、`console.warn`なしに実際に餌が配置され`food:hidden`イベントが発火する
  (`app.hideFoodDirect`内部にqaガードが無いため)。
- **suggested fix**: `main.ts`側で`if (config.qa && debugApiHandle) { ... }`とqaガードを追加する。
  影響は「4歳児向けの隠し場所ゲームの仕掛けを大人がコンソールで暴ける」程度で、外部通信や
  個人情報漏洩には無関係だが、契約違反であり修正コストは1行。

### R1-06 — DebugApi のメソッド一式が本番でも window に実体として存在する(仕様の字義との軽微な乖離)
- **severity**: minor
- **confidence**: high
- **evidence**: `src/debug/qa.ts:119-123`の`installDebugApi()`は`qaMode`の値に関わらず
  `DebugController`の全メソッド(`jumpTo`/`setTimeScale`/`setQuality`/`playBehavior`/`reset`)を
  `window.__ELEPHANT_GAME_DEBUG__`へ設置する。各メソッドは内部で`qaMode`チェックし本番では
  `console.warn`+no-opにフォールバックする(R1-05のような実害はない)ため、`docs/INTERFACES.md`の
  「本番でも ready/getState のみ露出」を「機能的には ready/getState のみが動く」という意味で
  読めば準拠しているが、「関数として存在するのは ready/getState のみ」という字義では非準拠。
  また、本番の`getState()`自体は`qaMode`に関係なく常に本物のハンドラを呼ぶため
  (`src/debug/qa.ts:37-40`にqaガードなし)、`session.hidden`(どのスポットにどの食材を隠したか)を
  含む完全な内部状態がconsoleから常時閲覧できる。「かくれんぼ」がゲームの核であるため、
  子ども自身がconsoleを操作する可能性は低いが、design上は答えを覗ける状態にある。
- **affected files**: `src/debug/qa.ts`, `src/main.ts`
- **reproduction**: 本番ビルドを`?qa=1`なしで開き、`window.__ELEPHANT_GAME_DEBUG__.getState().session`
  を見ると`hidden: [{spotId, food}, ...]`が確認できる。
- **suggested fix**: 優先度は低い(実害はR1-05ほど大きくない)。対応するなら`getState()`にも
  `qaMode`チェックを入れ、本番では`{ready}`のみを返す簡略版にする、または`session.hidden`を
  マスクする。

### R1-07 — Service Worker autoUpdate は仕様どおり動作するが、ゲーム進行中の無警告リロードのリスクがある
- **severity**: info
- **confidence**: high(vite-plugin-pwaの生成コードを直接確認)
- **evidence**: `vite.config.ts:11,30-36`(`registerType:"autoUpdate"`+`skipWaiting:true`+
  `clientsClaim:true`)、`src/main.ts:161`(`registerSW({ immediate: true })`、
  `onNeedRefresh`等のコールバック未指定)。
  `node_modules/vite-plugin-pwa/dist/client/build/register.js:38-42`:
  ```js
  if (auto) {
    wb.addEventListener("activated", (event) => {
      if (event.isUpdate || event.isExternal) window.location.reload();
    });
  ```
  新SWが`activated`になった時点(初回インストールでは`isUpdate`が偽なのでreloadしない)で
  **無条件に`window.location.reload()`**する。これは`docs/ARCHITECTURE.md`の「更新は新SW有効化時に
  リロードし、新旧バンドル混在を防ぐ」という設計どおりに動作しており、バグではない。
  ただし、hide/seekフェーズの途中(セッションの`hidden`/`found`はlocalStorageへ永続化されない、
  `src/save/save.ts`の`SaveData`は設定・album・firstPlayDoneのみ保持)でこのリロードが発火すると、
  子どもに何の予告もなくアプリが再起動し、その回のプレイ内容が失われる。発生条件は「タブを開いた
  ままの状態で新デプロイが行われる」ことなので頻度は低い。
- **affected files**: `vite.config.ts`, `src/main.ts`
- **reproduction**: 未実施(node_modules内のライブラリ実装コードで裏取りしたのみ、実機での
  再現テストは未実施)。
- **suggested fix**: 必須ではないが、`registerSW`に`onNeedRefresh`を渡して`registerType`を
  `"prompt"`寄りの挙動(hide/seek中は保留し、title/album等の安全なフェーズへ戻った時だけ
  reloadする)にする改善余地はある。

## 確認したが問題なしと判断した項目(根拠つき)

- **FSM本体**(`src/core/fsm.ts`): 不正遷移は`throw`せず`console.warn`+無視、これは仕様どおり。
  遷移は同期的に実行され`onChange`リスナーも同期発火するため、JS単一スレッド性により
  「連打による二重遷移」は起きない(遷移中に次のクリックが割り込む余地が無い)。
  `gate.ts`/`hide.ts`の完了ハンドラ(`triggerOpen`/`finishHiding`)も`opened`/`done`フラグで
  二重発火を防いでいる。
- **seek画面の中断後始末**(`src/ui/screens/seek.ts`): `cancelled`フラグで`run()`のループ・
  完了イベント・`setTimeout`後の`transition("album")`を全てガードしており、unmount時に
  `unsubComplete()`/`unsubArrived()`/`dots.dispose()`も呼ばれる。実装は健全。
- **イベントリスナー解除**: `mountXxxScreen`系はいずれも戻り値のunmount関数内で
  `ctx.events.on(...)`の解除関数を呼んでいる(`hide.ts`/`seek.ts`/`gate.ts`/`title.ts`/`album.ts`
  を確認)。`ui/app.ts`の`unsubFsm`は`currentUnmount?.()`を先に呼んでから次の画面をmountするため、
  画面遷移を繰り返しても購読が二重に積み上がらない。
- **three.js dispose**(`src/scene/environment/dispose.ts`, `world.ts`の`dispose()`/`placeFood()`/
  `clearFoods()`): `placeFood()`は既存メッシュを`disposeObject3D()`してから新規追加、
  `clearFoods()`も同様。geometry/materialの`dispose()`は三.jsの仕様上冪等なため二重呼び出しでも
  安全。`tests/unit/world.test.ts`の`"dispose() clears foods and does not throw when called twice"`
  で確認済み。なお`World`インスタンス自体は`main.ts`で1回生成されたまま再生成されない設計
  (`grep`で確認、`createWorld`の呼び出しは`main.ts`に1箇所のみ)であり、「再プレイでworld再構築」は
  実際には発生しない(`placeFood`/`clearFoods`の差分更新のみ)。
- **WebGL context lost/restored**(`src/scene/renderer.ts:36-46`): `preventDefault()`で既定の
  コンテキスト喪失を防ぎ、`contextLost`フラグで`render()`をスキップ、復旧時に
  `applyQuality`+`resize`を再適用する実装が存在する。実機でのcontext lostの実発火は未検証
  (R1-12参照)だが、コードパス自体は仕様に沿っている。
- **draw calls / triangles 予算**(目標 ≤120 dc / ≤250k tris、low: ≤70/≤120k):
  `src/scene/environment/*.ts`・`src/scene/effects/dust.ts`・
  `src/scene/elephant/behaviors/breakBranch.ts`・`src/scene/elephant/model.ts`で
  `BufferGeometryUtils`のマージ/`InstancedMesh`の使用を確認、多くの環境オブジェクトが
  個別`THREE.Mesh`ではなくマージ済みジオメトリで構築されている。実測値は`ops/reports/S6.md`
  記載の概算(quality=low時点でメッシュ数69、概算三角形数18,210、`renderer.info`未接続のため
